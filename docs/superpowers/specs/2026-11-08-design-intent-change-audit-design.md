# XX-Net 设计意图与变更损益审计设计

日期：2026-11-08

## 1. 背景与意图

本轮不是再次按文件平均扫描，也不是用现有测试通过证明系统没有并发问题。目标是站在第三方 QA 与资深开发工程师视角，在当前项目现状上还原功能契约，审计 2026-10-27 之后除日志压缩修复外的功能、性能、资源与可靠性变化，回答三个问题：

1. 每处变化原本想改善什么，实际改变了什么公共契约或执行顺序。
2. 变化是否让正常路径、异常路径、慢网络、高并发、旧调用方或停止中的模块承担未说明的代价。
3. 收益与损失能否用双向证据界定，并形成可复核的修复、有意权衡或设计裁定。

最终只能声明“已覆盖模型内收敛”，不能宣称不存在未知问题，也不能用离线复现反填历史生产事故根因。

## 2. 目标、非目标与反目标

### 目标

- 建立覆盖已提交和未提交逻辑变化的完整账本，而非只检查最近几个修复。
- 还原真实入口、launcher、front、Smart Router、X-Tunnel 及共享组件的职责、执行流、资源所有权和跨层契约。
- 对每个高风险变化同时检查优化收益、正常功能保持和异常资源回收。
- 将静态候选、动态复现、生产关联和设计裁定分开，确认的问题按 RED→GREEN 最小修复。
- 用 hunk 级覆盖分母、核心流程矩阵、独立 QA、测试清单和条件式生产验收定义停止条件。

### 非目标

- 不重新设计或重写网络栈，不为了“架构更漂亮”做大规模重构。
- 不评价日志压缩修复本身的内部算法；纯日志内容和格式变化不作为功能缺陷目标。其他日志变化若影响调用线程阻塞、公共接口、资源或模块生命周期，仍须审计这些外部影响。
- 不盲目扫描 `upstream/`、备份和第三方库；它们只作基线对照或必要的外部契约证据。
- 不把当前生产未启用的支持模块直接排除；其公共接口和离线契约仍纳入。
- 不通过调大超时、放宽断言、降低容量或牺牲正常功能制造测试通过。

### 反目标

出现以下任一情况，即使测试全绿也视为本轮失败：

- 只列发现，不用可机检分母证明变化已完整入账。
- 把提交说明当作代码事实，或把代理报告当作已确认缺陷。
- 只验证故障被抑制，不验证正常请求、合法对端和旧调用方仍可用。
- 用一次 204、短时无异常或重复 GREEN 宣称间歇故障永久治愈。
- 在修复中暗中改变 C/D 级契约、掩盖失败运行或扩大产品范围。

## 3. 基线与范围裁定

### 3.1 日期与历史边界

为避免日期语义造成漏审，2026-10-27 当天也纳入边界核查。仓库历史始于当天 `f1aa5bc`，其说明为“5.16.7.1 baseline + patches”；因此需额外列出根快照与 `upstream/XX-Net-5.16.7` 在真实产品路径上的差异。无法从 Git 证明来源或原始意图的既有补丁标为“历史意图未知”，不能当作不存在变化。

主行为基线采用 `68d8506`（2026-10-28，F/G 日志治理收尾），比较范围为：

- `68d8506..5dc3f12` 的已提交变化；
- 以 `5dc3f12` 为 HEAD 的当前工作树变化；
- `f1aa5bc..68d8506` 的日期/排除核查，确认没有漏掉非日志行为；
- 根快照相对上游参照树的产品差异，作为不可还原历史的补充清单。

规划时主线程已核对 `7738967..68d8506` 只有日志治理、文档、测试和备份产物；执行时仍须扩展到 `f1aa5bc..68d8506` 并逐项确认。规划快照中 `f1aa5bc..HEAD` 为 81 笔、`68d8506..HEAD` 为 69 笔，工作树有 43 个已跟踪文件修改，其中 29 个为 `code/default/` 产品 Python 文件；这些数字只用于规划，执行入口重新冻结。

### 3.2 产品与参照范围

产品范围是整个 `Coding/XX-Net-5.16.7.1/` 内实际参与安装、启动、运行或支持模块的文件，不限于 `code/default/`。顶层 `Coding/XX-Net-5.16.7.1/start` 已核实存在 iptables 创建、清理和退出语义变化，必须入账；installer、启动包装脚本及其他真实入口按同一规则检查。

`upstream/`、备份、旧部署和第三方库不计入产品变化分母，只在差异对照或契约证明时使用。生产版本以实际运行文件哈希为准，不能假定等于 HEAD 或当前工作树。

### 3.3 审计单位与 hunk 分母

审计单位是“逻辑变化”，不是提交或文件。一个提交可拆成多个逻辑变化，一个逻辑变化也可跨多个提交和文件。ID 分为：

- `CHG-C-<nnn>`：已提交逻辑变化；
- `CHG-W-<nnn>`：仅工作树新增的逻辑变化；
- `EXC-<nnn>`：排除项；
- `DEC-<nnn>`：设计裁定；
- `RSK-<nnn>`：风险或候选缺陷。

同一逻辑行为若部分已提交、部分在工作树，拆成 C/W 两项并用 `related` 关联，不能合并来源。混合提交和混合文件必须拆分。风险或设计 ID 不能代替变化/排除 ID 完成覆盖。

覆盖分母来自以下集合并集，而非只取首尾净 diff：

1. 每个纳入提交触过的路径及全部功能 hunk，包括后来被反转的净零变化；
2. 当前工作树 tracked diff 和声明范围内的 untracked 文件；
3. 删除、重命名和根快照补充差异。

每个 hunk/删除/重命名记录映射到 CHG-C、CHG-W 或 EXC。每项变化至少有一个真实历史或当前源码锚点，删除项可指历史位置。文件集合、变更记录集合与账本投影做集合相等校验；孤儿、未映射 hunk、无依据排除均为零。纯文档、测试和证据变化单独建分母，不与产品代码混淆。

## 4. 被审计快照与变更控制

阶段 1 冻结的是不可变的“被审计输入快照”：产品路径集合、测试清单、每个文件的哈希及对应历史 diff。证据目录、审计报告和审计工具自身的写入不触发重新冻结。

- 审计过程中确认的产品修复记为原 CHG 项的新 `revision`，保存原始指纹、修复指纹和关联 RSK；不伪装成原始范围的新变化。
- 与原缺陷无关的新产品行为必须新建 CHG-W 项并扩大分母。
- 测试和审计工具的修订记录在同项 revision 中，不改写原始 RED 证据。
- 无法阻止其他写入者，但每个阶段入口及部署瞬间都重新比对待审路径哈希；发现外部漂移即停止当前验收，更新分母后重跑受影响证据。
- QA 后产品文件若变化，完整离线验收失效；部署清单必须与最后一次完整验收的快照哈希一致。

历史基线对照只读取 Git 对象并写入新的空临时目录，不 checkout、覆盖或清理当前工作树；运行时使用 `python3 -I` 并隔离 import、配置和依赖来源。

## 5. 功能契约与核心流程模型

### 5.1 每个组件必须记录的契约

| 维度 | 必须回答的问题 |
|---|---|
| 功能承诺 | 调用方可依赖什么参数、返回值、完成和异常语义 |
| 执行流 | 哪些线程、回调、队列、计时器和 selector 参与 |
| 共享状态 | 哪些字段被多个执行流读写，共同状态边界在哪里 |
| 锁与等待 | 锁顺序、condition 等待谓词、唤醒者、持锁外部回调及重入路径 |
| 提交资格 | 哪个对象、attempt、generation 或 incarnation 有权提交结果 |
| 资源所有权 | socket、队列项、缓存项、线程和缓冲区由谁创建、接回、关闭 |
| 生命周期 | 启动、半启动回滚、停止、替换、重启和最终持久化顺序 |
| 时间与重试 | 使用墙钟还是单调钟，期限是否共享，重试由谁认领 |
| 外部约束 | HTTP/1、HTTP/2、DNS、SOCKS 等协议允许和禁止的行为 |
| 兼容面 | 旧调用方、未启用模块、不同 front 实现是否仍满足接口 |

异步交接必须分别记录“事件发生”和“实际执行”。CodeGraph 用于定位符号、调用链和影响面；契约结论必须回到真实源码。文档没有说明的设计意图标为未知，不补写故事。

### 5.2 核心流程覆盖分母

核心流程不是主观印象，执行前固定为以下“模块×流程”清单，并为每项记录入口、交接点、资源终点和正常/异常/停止/代际交错矩阵：

1. 顶层安装/启动/iptables 与 launcher 启动、半启动、停止、重启、控制面并发。
2. front request 正常完成、重试、超时、停止；H1/H2 建连、SETTINGS、发送、接收和关闭。
3. 独立 Client 建连、完整写入、复用、不完整响应和共享 HTTP handler 接回。
4. DNS 缓存、平行查询、CNAME、退避、全调用期限和停止。
5. Smart Router Direct/Socks/GAE 回退、PipeSocks 交接、连接池和监听重启。
6. X-Tunnel Session/Conn 创建、首包、发送、ACK/重试、login/report、背压、reset/stop。
7. 配置与缓存 save/load、脏位、最终持久化及 IpManager 代际。
8. 当前未启用但受支持的 front/TLS Relay 等模块的公共入口与离线契约。

“高风险/高优先级”包括所有潜在或确认的 Critical/Important，无论证据是 R 还是 S。每个核心流程必须关闭或明确保留其高风险项；不能只写“核心已覆盖”。

## 6. 变更账本、证据与风险状态

### 6.1 账本字段

每项逻辑变化至少记录：稳定 ID、来源提交/工作树指纹、hunk/文件/符号、原意图及证据、修改前后代码事实、公共契约、受益者、收益指标、可能受损路径、兼容性、关联测试及其证明边界、RSK/DEC、处置和 revision。

### 6.2 五轴分离

以下五项不得混为一个分数：

1. **代码行为证据**：R 为真实代码加可控替身的确定性复现；S 为源码可推出但未动态复现；C 为需设计裁定。
2. **契约状态**：保持、明确兼容变化、意外破坏或尚未知。
3. **影响严重度**：Critical、Important、Minor。
4. **生产可达性**：当前启用可达、支持但未启用、仅参照树或未知。
5. **事故归因**：生产日志关联、仅本地行为证明、无生产关联。

S 级候选不是已确认缺陷；R 级复现不证明历史生产根因；C/D 级事项不得擅自改成代码修复。独立审查只产生候选，重要发现由主线程核对真实实现。

### 6.3 严重度与终态阻断矩阵

- **Critical**：可信路径导致跨层状态破坏、死锁、数据/字节错误、无法停止或严重失控资源消耗。
- **Important**：可信路径导致正常功能退化、错误重试/完成、陈旧状态提交、连接或线程持续泄漏。
- **Minor**：影响有限且有明确边界的兼容、清理或可维护性问题。

| 状态 | 能否关闭关联变化/契约 | 收敛要求 |
|---|---|---|
| R + Critical/Important | 修复并有最终代码 GREEN 后才能关闭 | 未修复即阻断，除非用户明确保留 |
| S + 潜在 Critical/Important | 不能关闭 | 补证、以证据改级或明确未收敛；不得转为 deferred |
| R + Minor | 可 deferred | 记录触发条件、代价和边界 |
| C/D 设计裁定 | 不能当作缺陷已解决 | 用户裁定或保持开放，不擅改代码 |
| 核心契约尚未知 | 不能关闭 | 补契约证据或明确未收敛 |
| 依赖未覆盖环境的高风险项 | 不能关闭 | 保持未覆盖/收益未证实并阻断其卡片结论 |

真实 H2 peer、多阶段 Smart Router 故障注入、Client 第二次真实复用等可作为全局残余缺口保留，但依赖这些证据的变化或契约必须同时标为未覆盖，不能局部显示已关闭而只在总报告附一句限制。

## 7. 平衡点与双向验收协议

平衡点不是任意折中值，而是一组预先登记、可判 PASS/FAIL/INCONCLUSIVE 的约束：

1. **工作负载与版本**：每张性能/资源卡在运行前登记真实产品工作负载、环境指纹、基线/修改前/最终代码指纹及隔离方式。
2. **指标与 oracle**：登记延迟、吞吐、FD/线程/RSS/队列等目标指标，以及正常功能、协议兼容和资源回收 oracle。
3. **重复与噪声**：运行前登记最少独立运行次数、统计量、噪声预算和无效运行规则；噪声超过预算只能判 INCONCLUSIVE，不能挑最好一次。
4. **损失与资源边界**：运行前写明可接受损失、容量/期限/重试边界、触发条件、影响对象和恢复方式；不能事后选择阈值。
5. **最终复验**：至少比较基线、修复前和最终代码；最小修复若撤销原收益，必须更新裁定，不能沿用修复前的收益结论。

可靠性修复可用确定性行为命题证明收益。性能优化没有有效真实产品测量时只能标“收益未证实”。`tests/performance_baseline.py` 已核实为合成指标和账本自测，不得作为代理性能提升证据。外部公网只作运行 sanity，不作为稳定性能基准。

所有高风险项同时验证：正常路径不退化、目标异常得到控制、相邻异常不转化为死锁/泄漏/错误提交。无法由兼容性、协议、现有设计和用户目标裁定的取舍进入 DEC 清单。

## 8. 实施阶段与入口/出口门槛

### 阶段 1：冻结与完整入账

建立不可变输入快照、hunk 分母、核心流程清单和测试 manifest。

**出口**：产品文件、hunk、变化/排除 ID 双向集合相等；日期边界、根快照、混合提交、删除/重命名和真实入口均已处理。

### 阶段 2：契约与执行流还原

按共享 Task/front、Smart Router/DNS/PipeSocks、X-Tunnel、launcher/共享 HTTP/配置持久化分组，优先公共契约和跨层交接。

**出口**：核心流程矩阵每项都有入口、锁/等待、交接、资源终点及正常/异常/停止/代际模型；未启用支持模块有离线契约结论。

### 阶段 3：损益筛查与风险排序

逐项建立“原意图—代码事实—受益—受损—证据—处置”卡片。

**出口**：每项变化有处置；所有高风险项有冻结的验证命题、正常/异常 oracle 和必要数值边界，不能只凭历史 GREEN 关闭。

### 阶段 4：确定性验证与平衡点审计

入口要求阶段 3 的命题与 oracle 已冻结。复用事件门、真实 socketpair、故障 selector、受控时钟和真实状态锁；每个确认修复先有准确 RED，夹具错误修正后重新取得 RED。

**出口**：高风险项有可重跑证据；性能/资源变化有预先协议的收益与损失结果；C/D 项单列，未夹带产品修改。

### 阶段 5：最小修复与关联回归

入口只包含 R 级 Critical/Important 或已批准的 DEC。保持公共参数、返回语义和资源所有权，除非规范明确批准变化。

**出口**：每项修复通过目标异常、正常路径、相邻异常和关联套件，并对最终代码复验原收益/损失；Minor deferred 有明确代价。

### 阶段 6：独立 QA、完整回归与条件式生产验收

独立 QA 检查覆盖分母、契约误读和反例。完整测试 manifest 在执行前冻结，记录每项命令、加载代码根、文件哈希、退出码、用例/场景数、skip、超时和重试；失败运行不得被后续 GREEN 隐去，未声明 skip 和漏项均阻断。

只有本轮实际产生产品修复、用户批准的执行范围包含部署且全部离线门槛通过时才部署。纯审计、有意保持或未获部署授权不触发部署，也不要求做部署后验收。

**出口**：独立 QA 无未处理高优先级项，manifest 中完整离线验收通过；若实际部署，哈希、真实进程代际、必要端口、控制接口、真实代理路径和脱敏窗口日志均通过，失败则恢复并验证旧版本。未部署则明确记录“未部署，未做部署后验收”。

## 9. 测试与生产证据协议

测试 manifest 覆盖全部 `tests/test_*.py`、明确的离线独立 acceptance/probe 脚本及本轮新增测试；生产黑盒单列，不混入离线套件。每文件独立进程并设预先登记的超时。重试只用于已记录的环境/flake 调查，首次失败永久保留；不能用反复重跑至绿替代根因分析。完整扫描 FAILED、NO TESTS RAN、未捕获 `Exception in thread` 和意外 skip，故障注入的已捕获 Traceback 如实计数。

生产数据规则：

- 原始生产日志、完整配置响应和代理诊断原文不进入工具输出、报告或证据目录；只由本地采集器在进程内读取并输出脱敏派生结果。
- 禁止采集账号、密码、token、Authorization、Cookie、session_id、完整 URL/query；Host、DNS 名称和 IP 默认散列或掩码。
- 可保留时间、级别、事件名、错误类别、文件/函数/行号、计数和哈希；异常消息同样脱敏，测试夹具与命令输出遵守相同规则。
