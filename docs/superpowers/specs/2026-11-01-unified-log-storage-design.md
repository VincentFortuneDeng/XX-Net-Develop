# XX-Net 统一日志存储与有界错误上下文设计

## 背景与意图

当前每个模块同时存在启动日志、warning 日志、管理页内存缓冲和诊断快照。它们来自同一日志事件，但用途和保留策略不统一：WARNING 可能重复落盘，启动预算用完后的 DEBUG/INFO 又不再持久化，运行中发生 ERROR 时经常缺少前置现场。

用户已同意按推荐方向规划：在长期 WARNING/ERROR 历史与出错前的有限 DEBUG 现场之间取得平衡，减少不必要的文件重复，不追求无限完整审计。

本文是设计裁定与实施边界，不代表生产代码已经修改或部署。

## 目标

1. 每个已有磁盘日志的模块只维护一份权威滚动正文，启动、warning 和诊断视图按需从正文生成。
2. 保留现有启动阶段的完整初期日志能力。
3. ERROR 正文和异常堆栈始终记录；在固定成本内补充出错前的近期 DEBUG/INFO 上下文。
4. 保持现有 `xlog.debug/info/warn/warning/error/exception/critical` 业务调用方式和管理页增量 JSON 接口兼容。
5. 所有常态文件、内存和单次上下文导出都有明确上限，不增加后台定时线程。
6. 保留现有 `LogThrottle`、suppressed 计数和真实 stop/reset/close 生命周期尾账。

## 非目标与反目标

- 不实现无限 DEBUG 落盘、集中式日志平台、完整 JSON 日志框架或全局后台 flush。
- 不修改网络重试、路由、Queue、传输、DNS 或模块生命周期业务逻辑。
- 不保证进程异常退出时内存计数和近期上下文一定落盘。
- 不把同模块近期上下文解释为已证明的因果链；并发下它只是排障线索。
- 不在本次设计中部署、重启、删除生产旧日志或制作上游交付包。

## 当前兼容约束

- Launcher、Smart Router、GAE Proxy、X-Tunnel、cloudflare_front、seley_front、tls_relay 当前各自有 `start_log_<name>_<time>.log` 与 `<name>_warning.log`。
- `Logger.log()` 已用同一把 `buffer_lock` 保护文件写入和内存编号，可将统一文件与上下文快照留在这一现有并发边界内。
- 8085 日志页通过 `get_last_lines/get_new_lines` 读取内存字典，不读取磁盘文件。
- 诊断打包同时收集内存快照和磁盘 `.log`；旧 `reset_log_files()` 会删除旧启动文件并重开 warning 文件。
- cloudfront_front 当前没有自己的 `log_path`，本轮不为其新增持久文件。

## 总体结构

每个已有磁盘日志的模块改为：

```text
业务 xlog 调用
  → Logger.log() 同一锁内格式化
  → 内存环形缓冲：继续供 8085 页面读取，也供 ERROR 上下文筛选
  → 权威正文 <name>.log：按持久化策略写入
  → 达到大小上限时滚动为 <name>.log.1

启动视图 / warning 视图 / 诊断包
  → 按需读取并过滤权威正文，不常驻第二份正文
```

权威文件名对应为 `launcher.log`、`smart_router.log`、`gae_proxy.log`、`x_tunnel.log`、`cloudflare_front.log`、`seley_front.log`、`tls_relay.log`。旧 `start_log_*` 与 `*_warning.log*` 在切换后只作为历史文件存在，不由新运行路径继续追加。

不在每行增加 boot_id 或 JSON 包装，保持现有时间戳和级别文本格式。Logger 在内存记录本次启动时间和启动详细期结束时间，供运行期视图过滤。

## 持久化策略

| 事件 | 启动详细期 | 启动详细期结束后 |
|---|---|---|
| DEBUG | 写入权威正文和内存 | 默认只进内存；显式 `persist=True` 时落盘 |
| INFO | 写入权威正文和内存 | 默认只进内存；显式 `persist=True` 的重要生命周期/配置事件落盘 |
| WARNING | 写入权威正文和内存 | 写入权威正文和内存，沿用业务节流 |
| ERROR / exception | 写入权威正文和内存 | 正文与堆栈始终写入，并按上下文规则附加近期现场 |
| CRITICAL | 写入权威正文和内存 | 始终写入，并按 ERROR 相同规则附加上下文 |

启动详细期沿用各模块现有 `save_start_log` 行数预算：Smart Router 200、Launcher/GAE Proxy 500、X-Tunnel 及现有三个 Front 1500。预算用完后不再常态持久化普通 DEBUG/INFO，而不是关闭权威文件。

新增可选关键字 `persist=True`，供少数重要 DEBUG/INFO 调用显式持久化。未标注的现有调用保持原样；不得在首轮把普通 per-request INFO 全部改为持久化。首批只考虑启动/停止、模块配置改变、front 生命周期等低频事件，具体调用点在实施计划中列举。

`keep_log`/`full_log` 兼容为“启动预算结束后仍保持详细级别可落盘”，但不再表示无限保留；统一大小滚动上限始终有效。

## ERROR 有界上下文

### 来源与内存

复用现有 `Logger.buffer`，不新建第二份 DEBUG 环形缓冲。每次 ERROR/CRITICAL 在自身入-buffer 前，从同一模块已有条目中筛选最近的 DEBUG/INFO：

- 最多 40 条；
- 包含头和尾的整个上下文块最多 16KiB；
- 只取完整日志行，不截断 UTF-8 字符；
- buffer 较小或为零时自然减少或没有上下文；
- 不读取其他模块，不新增请求正文、凭据或其他当前日志没有的数据类别。

内存中已有条目的编号和 `get_new_lines()` 行为不变。上下文块只写权威正文，不回填内存，避免管理页重复显示和递归触发。

### 冷却与异常语义

- ERROR/CRITICAL 正文始终写入，上下文冷却绝不能抑制错误本体。
- 上下文按 `(logger.name, 原始 fmt 模板)` 使用 60 秒冷却；同一模板重复出错时不重复导出相同内存现场。
- `exception()` 的一次调用最多产生一个上下文块；其 `Except stack` 不再次导出上下文。
- 并发下在 `buffer_lock` 内完成筛选、冷却判定和整块写入，一个上下文块不能与另一块交错。
- 上下文块使用 ERROR 级头尾标记 `ERROR_CONTEXT_BEGIN/END`，中间保留原始行。warning 视图识别并保留完整块，不能只按单行级别过滤后丢掉中间现场。
- 上下文表示“同模块最近日志”，不标注为同一连接或确定因果。

不为上下文增加后台线程、网络操作或递归 `xlog` 调用。

## 权威文件滚动与失败行为

- 默认每个模块主文件 10MiB，只保留一个 `.1`，与当前 warning 文件上限一致；七个现有持久 Logger 的常态正文总上限仍约 140MiB，但不再额外累积新的启动/warning 双份正文。
- 以 UTF-8 字节数计算尺寸。普通日志行和上下文块作为写单元；写入前检查空间，需要时先滚动，上下文块不得跨主文件和 `.1` 拆分。
- 单条格式化日志硬上限为 64KiB，且不得超过当前文件大小上限。超限时采用中部省略：保留 UTF-8 完整字符的首尾和原始字节数标记，不整行丢弃，也不允许单条日志撑破文件上限。上下文块的有效上限同样不得超过当前文件上限。
- 同一模块第二次滚动替换旧 `.1`，不产生 `.2`。
- 打开 Logger 时若主文件已超限，沿用初始化滚动。
- 滚动或打开失败时保持当前失败安全原则：内存和管理页继续工作，磁盘写入跳过或尝试重开；不得递归写错误日志。
- 文件锁仍只覆盖内存操作和本地写入，不覆盖网络、Queue 或业务锁。

## 视图、管理页与诊断包

### 管理页

现有 `/log?cmd=get_new` 和管理页 500ms 轮询不变，仍读取内存，不回读权威文件，也不因磁盘故障阻塞。

### 启动视图

Logger 记录 `boot_started_at` 和 `startup_verbose_ended_at`。启动视图从当前 `.1`（如需要）和主文件中筛选本次启动详细期内的所有级别；详细期尚未结束时截止到当前。该视图是导出结果，不再常驻 `start_log_*` 文件。

每个模块由自己的 Logger 生成视图，并通过现有 control `/log` 接口增加 `cmd=export&view=startup|warning&max_bytes=...` 导出；Launcher 的 `/log` 使用同一约定。X-Tunnel 的诊断打包器只通过本机 HTTP 请求各模块视图，不直接访问其他进程的 Logger 内存，也不新增跨进程共享文件。单次启动视图默认最多 256KiB，warning 视图默认最多 512KiB，均优先保留时间最近的完整记录。

### warning 视图

从权威正文筛选 WARNING/ERROR/CRITICAL，并完整保留 ERROR_CONTEXT 块。诊断打包可直接把过滤结果写入 zip，不先在 `data/downloads` 常驻第二份 warning 正文。

### 内存诊断快照

现有 `downloads/*_log.txt` 表示“打包时的易失内存快照”，与权威正文用途不同，可以保留；诊断包应避免同时无差别打入旧 start/warning 文件和统一正文造成重复。统一模式下默认打权威正文、必要视图和当前内存快照，旧格式历史仅在显式要求时加入。

诊断包仍默认总预算 10MiB，按以下优先级装入，预算不足时跳过低优先级条目：

1. 当前系统/模块状态、debug 文本和已脱敏配置；
2. 当前内存快照；
3. 各模块有界启动视图和 warning 视图；
4. 统一主正文，按修改时间从新到旧，只加入能完整放入剩余预算的文件；
5. 统一 `.1`，仅在仍有预算时按同样规则加入。

`pack_logs(max_size, include_legacy=False)` 默认排除旧 start/warning 历史；调用方显式传 `include_legacy=True` 时才在最后优先级加入。首轮不新增 Web 开关，诊断下载保持默认 `False`。大文件不能完整放入时跳过并继续尝试后续较小条目，不以半个文件冒充完整正文。

## reset 与旧文件迁移

- 统一模式的 `reset_log_files()` 只 flush/重开权威文件并保持滚动上限，不删除旧启动历史，不重置内存日志编号。
- `save_warning_log=True` 暂时作为统一持久文件的兼容入口；可新增语义更准确的 `save_persistent_log=True` 别名，但不要求首轮修改所有 `getLogger` 调用。
- `warning_log_fn` 等纯内部名称可以迁移；对外模块方法和 Web JSON 格式不变。
- 首次部署前备份旧日志。部署后旧 `start_log_*`、`*_warning.log`、`*_warning.log.1` 保留为只读历史，不由程序自动删除或覆盖。
- 切换版本期间如需双写验证，只能在离线测试或显式兼容开关下进行；最终常态默认不能双写两份正文。

## 验证要求

必须为以下行为先写失败测试，再做最小实现：

1. 启动预算内所有级别进入同一权威文件；预算后普通 DEBUG/INFO 不落盘但仍能从管理页取得。
2. `persist=True` 的低频 INFO 在预算后落盘；WARNING 以上保持原行为。
3. 首个 ERROR 带出最近且不超过 40 条/16KiB 的完整上下文；同模板 60 秒内第二个 ERROR 正文仍写、上下文不重复。
4. `exception()` 只带一个上下文块和一份堆栈；CRITICAL 行为一致。
5. 多线程 ERROR 的上下文块不交错，内存编号连续，管理页轮询兼容。
6. 主文件滚动只留一代，初始化滚动、非 ASCII 字节计数和上下文块不拆分均正确；超过 64KiB 或测试文件上限的单行按首尾保留且绝不撑破上限。
7. 滚动/打开失败不递归、不影响内存读取；磁盘恢复后按既有失败安全语义继续。
8. 启动视图、warning 视图与 ERROR_CONTEXT 块过滤正确；各模块 export 接口只读取本进程 Logger；诊断包遵守视图上限、10MiB 总预算、优先级、完整文件和 include_legacy 规则，不默认打入重复旧格式正文。
9. reset 不删除权威历史、不重置内存编号；keep/full_log 仍受大小上限约束。
10. 现有 LogThrottle 38 项及后续扩展、五套既有回归、fd 探针和所有模块 py_compile 继续通过。

生产核验只能在另行批准部署并由用户重启后进行。文件部署不等于新进程加载；未发生 ERROR 时只能记录“上下文路径未触发”，不能用离线测试替代生产疗效。

## 本次设计裁定

以下是本次为可实施性确定的默认值，并非用户逐项指定：10MiB 单代滚动、40 条/16KiB 上下文、60 秒同模板上下文冷却、复用现有内存 buffer、保持文本格式、旧文件只读保留、不新增后台线程。独立 builder 审查后进一步明确：各模块通过本机 Web 接口导出自己的视图；启动/warning 视图分别限 256/512KiB；诊断包按状态与近期现场优先的固定顺序使用 10MiB；`include_legacy=False` 为默认；超长单行最多 64KiB 并中部省略。这些是为消除实施歧义而作的设计裁定，实施计划可以在不改变上述目标的情况下选择最小代码结构；任何放宽上限、增加双写常态或抑制 ERROR 本体的变化都必须重新审查。
