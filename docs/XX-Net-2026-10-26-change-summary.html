4. 日志节流的核心逻辑

4.1 通用 LogThrottle(60)：按 key 的固定窗口闸门

事件到达 + key
   │
   ├─ 该 key 当前没有有效窗口 ─→ 放行首条 WARN，建立 60 秒窗口
   │
   ├─ 窗口内再次到达 ─────────→ 不写 WARN；suppressed += 1；业务照常执行
   │
   └─ 下一窗口事件到达 ───────→ 放行一条，附上一窗 (suppressed N)，开始新窗口
保留什么
每个 key 的首条信号、下一窗口的数量结算；放行行保留原始字段。
不保留什么
窗口内重复事件的逐条文本；M 已在五个真实 stop/reset 终点结算尾账，但 HEAD、沉默剪枝和进程异常退出仍可能丢失最后的数量注解。
容量语义
超过 512 个 key 会触发剪枝，但只删除过期 key；活跃 key 可以超过 512，并非硬上限。
线程语义
allow/flush 共用类内部锁；flush 封住旧生命周期，reset 显式重开；调用方仍需保证“日志账本”和“业务状态”的生命周期一致。
逻辑边界：M 的 flush 只返回聚合总数与有待结算计数的 key 数，并清空账本；不缓存或补打被抑制日志原文。它覆盖 dispatcher、_connect_ssl、transfer、front retry 和 SN 的真实 stop/reset；http1 的类级 HEAD 账本不能随单个 worker.close 清账，保持下一窗结算。异常退出仍无法保证尾账。
M 已采用生命周期 flush：只在真实 stop/reset 终点结算，每对象最多一条汇总 WARN，无后台定时器，不逐 key 打印；长期模块级、无终点账本仍不引入全局脉冲。

4.2 并非所有限流都使用 LogThrottle

机制 / 位置键与窗口结算方式是否影响业务
send-block / pipe_socksid(socket)，1 秒下一放行附 suppressed；socket close 时 final 清账仅日志
no-IP / connect_manager每个 ConnectManager 一套旱态账本，60 秒放行附上一窗；恢复时补尾窗和 total仅新增日志
no_ip_time 原功能未改
IPv6 skip / ip_manager探测周期 300 秒每个周期按实际 skip 数写 INFO，无 suppressed 账本会过滤前端
DNS backoff / dns_querynameserver，60 秒发送成功清账；到期重试；全冷却单点 fail-open会改变 DNS 选择
通用 LogThrottle调用方定义 key，通常 60 秒下一窗口附 suppressed；M 在真实 stop/reset 终点汇总清账仅日志
warning_log 滚动单文件 10MB当前文件→.1，只保留一代日志存储行为

6. 判断逻辑是否有问题：建议重点看这 10 项

#审查问题当前设计与判断入口
1日志被抑制时，业务是否也被跳过？除 DNS/IPv6 等明确标记“行为”的项目外，allow 只包围日志语句；Queue、重试、状态更新必须仍在 allow 之外。I/J 测试专门验证了这一点。
2key 是否过细，导致节流失效？F 的完整 URL 含 tid 就是过细；I 改为去查询参数 endpoint。key 必须对应“要聚合的故障对象”，而非日志字符串。
3key 是否过粗，导致不同故障被混合？connect_ssl 加异常类别；x_tunnel 加 kind；dispatcher 不区分 retry/timeout/status、HEAD 不区分三出口，是有意的聚合取舍。
4reset 后是否沿用旧窗口？x_tunnel 使用事件所属 session；J 在 reset 锁内替换 throttle。若只看 transfer_no/SN 而不看生命周期，就可能错账。
5尾账是否必须落盘？send-block 有 close、no-IP 有 recovered；M 为五个真实 stop/reset 终点补一条聚合尾账并清账。HEAD、沉默剪枝和进程异常退出仍可能丢最后的数量注解。若需要完整审计，应另做事件统计，而不是把 WARN 当审计流。
6静默事件是否也计数？J 的旧/重复 t 原本无日志，因此不能调用 allow。否则 suppressed 会包含“从未打算打印的事件”，并吞掉跨窗放行。
7退避是否可能造成完全无出口？DNS 全冷却时选择最早到期的一台 fail-open；IPv6 全被过滤后可能无 front，但 no-IP 会报警，这是资源真实不可用，不应伪造可用。
8日志降级是否掩盖真正异常？reserved/frag 和预期 selector 竞态降 DEBUG；未知 Exception 仍 ERROR。no-module 仅未启用路由降噪，启动失败 WARN 未动。
9生产证据是否足够？F/G 有窗口对比，H 有 connect_ssl 与 total 实证但 DNS 未触发；I 已出现首批独立首报但尚无同窗聚合样例，J 未触发。不能用“没有相关日志”代替疗效。
10日志存储是否有长期保留语义？warning_log 只保留主文件和一代 .1；需要历史分析时必须依赖独立归档，不应把滚动文件当永久历史。
总体逻辑结论：当前设计的主线是“保留每个独立故障对象的首报，压缩同对象同窗重复，并在有明确生命周期终点时结算尾账”。它不是全局静默，也没有把网络失败当作已修复。真正需要持续审查的是 key 的生命周期、不同事件是否被过度合并，以及新版本的生产回归。
